## Головний принцип

Для будь-якої нової задачі по сайту спочатку пропонувати і реалізовувати **найпростіше дієве рішення, яке повністю закриває потребу користувача**.

Не ускладнювати архітектуру, інтерфейс або workflow без реальної необхідності.

## Порядок прийняття рішення

1. Спочатку знайти мінімальне рішення з найменшою кількістю нових сутностей, станів, меню, кнопок, залежностей і коду.
2. Якщо воно повністю вирішує задачу — на ньому зупинитися.
3. Складніший варіант розглядати тільки тоді, коли простий не покриває конкретну вимогу, має очевидний технічний ризик або не масштабується в уже підтвердженому сценарії.
4. Не додавати функції «на майбутнє», якщо користувач їх не просив і вони не потрібні для надійності.
5. У UI надавати перевагу простому прямому сценарію перед вкладеними dropdown, preview, додатковими панелями, режимами та дублюючими елементами.
6. У CORE надавати перевагу локальній зміні перед новою підсистемою, якщо локальна зміна безпечно вирішує задачу.
7. Якщо є два однаково дієві варіанти — вибирати той, який легше зрозуміти, перевірити, підтримувати й відкотити.

## Контрольне питання перед реалізацією

Перед внесенням змін обов'язково перевірити:

**«Чи можна це зробити простіше, не втративши функціональність і надійність?»**

Якщо відповідь «так» — використовувати простіший варіант.

## Поточний приклад

Для індикації нової пошти у Boss достатньо звичайного пункту `Пошта` з маленьким badge/плашкою з кількістю непрочитаних. Клік веде безпосередньо в пошту. Dropdown, preview останніх листів або складна навігація у верхньому меню для цього не потрібні.

Цей принцип має застосовуватися в усіх наступних гілках роботи над mavik.name незалежно від конкретного релізу.
