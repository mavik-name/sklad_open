# MAVIK.NAME — R230 MAIL BROADCAST CHECKPOINT

Дата: 2026-08-30
База: **R229 (CANONICAL / ONLY WORKING BASE)**
Статус R230: WORK IN PROGRESS / NOT CANONICAL

## Мета
Зробити масове розсилання в Boss таким, щоб:
1. кожен адресат отримував окремий лист;
2. адресат не бачив інших адрес із розсилки;
3. власник бачив окремий результат відправлення по кожній адресі;
4. через деякий час можна було перевірити журнал і зрозуміти, кому лист був переданий SMTP-серверу успішно, а кому ні.

## Жорстка серверна логіка
- НЕ надсилати один RFC-лист із кількома адресами в `To:`.
- НЕ покладатися на BCC як основний режим масової розсилки.
- Кожна введена адреса = окрема SMTP-відправка.
- Для кожного адресата формувати окремий видимий заголовок `To: recipient@example.com`.
- Інші адреси цієї розсилки не повинні бути присутні в `To`, `Cc`, `Bcc` або інших видимих заголовках.
- Для кожної адреси генерувати окремий `Message-ID`.
- HTML + plain-text alternative R229 зберегти.
- Тема, HTML/text body і вкладення можуть бути спільними для всієї пачки, але SMTP/message envelope формується окремо для кожного адресата.

## Результат SMTP
Для кожного адресата окремо фіксувати:
- email;
- timestamp;
- статус `accepted` / `failed`;
- Message-ID;
- короткий SMTP result/error без паролів і секретів.

Після розсилки показувати в Boss таблицю, наприклад:

| Адреса | Статус | Message-ID |
|---|---|---|
| a@example.com | ✓ сервер прийняв | ... |
| b@example.com | ✓ сервер прийняв | ... |
| c@example.com | ✗ помилка | ... |

Підсумок: `Успішно: X із Y`. Якщо є помилки — вони не маскуються загальним зеленим статусом.

Термінологія в UI: не писати «доставлено адресату», якщо є лише SMTP acceptance. Коректно: **«Сервер прийняв лист»** / **«Помилка відправлення»**.

## Надіслані
- Після успішного SMTP кожен окремий лист додавати в IMAP `Надіслані` окремою копією, якщо папка доступна.
- Помилка IMAP append не повинна міняти вже успішний SMTP-статус.
- Для пачки з N успішних адрес у «Надісланих» має бути N окремих листів, кожен зі своїм `To:` і `Message-ID`.

## Журнал розсилок
Додати protected runtime log, рекомендований шлях:
`/_site-state/mail-send-log.json`

Зберігати без тіла листа:
- batch_id;
- subject;
- created_at;
- recipient;
- status;
- message_id;
- smtp_result/error;
- sent_append status.

Не зберігати SMTP пароль, токени, auth transcript або тіло листа.

Boss має показувати історію розсилок: дата/тема/кількість адрес/успішно/помилки, з можливістю розкрити конкретну пачку і побачити кожного адресата.

## Поля адресатів — UI
- Поля email зробити компактнішими по висоті/ширині, без великих textarea.
- При відкритті форми показувати одне поле адресата.
- Коли поточне поле містить валідну email-адресу, автоматично показувати наступне порожнє поле.
- Нові порожні поля не створювати наперед пачкою.
- Якщо користувач очищає зайві кінцеві поля, вони можуть автоматично прибиратися.
- Перед Send показати точну кількість розпізнаних унікальних адрес.
- Дублікати адрес дедуплікувати з видимим повідомленням, а не надсилати двічі випадково.

## BCC
BCC можна залишити як окрему ручну функцію для звичайного листа, але **масова адресна стрічка R230 не повинна залежати від BCC**. Якщо BCC використовується в режимі масової розсилки, його семантика має бути чітко визначена й не повинна розкривати інші адреси.

## Валідація R230
Обов'язкові тести до видачі:
1. 3 адресати → 3 окремі message payloads.
2. У кожного payload `To:` містить тільки поточного адресата.
3. Жодна інша адреса пачки не присутня у headers/body.
4. 3 унікальні Message-ID.
5. Симуляція: 2 SMTP accepted + 1 SMTP failed → UI показує 2/3 і конкретну помилку третього.
6. IMAP append виконується тільки для SMTP accepted адрес.
7. Журнал містить окремі записи по всіх 3 адресах.
8. Дубль адреси в UI не породжує друге відправлення.
9. Поля адрес з'являються по одному після валідного попереднього.
10. Чернетка з кількома адресами відновлює послідовні поля коректно.

## Канон
R229 залишається єдиним каноном. R230 не отримує канонічного статусу без прямого затвердження автора після встановлення і перевірки.
