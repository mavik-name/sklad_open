# MAVIK.NAME — LOCALE STORAGE CANON

Дата: 2026-08-19
Статус: **HARD STORAGE CANON / ПРІОРИТЕТ НАД РАНІШИМИ ТРАКТУВАННЯМИ STORAGE**

## Головний принцип

**Папки локалей існують тільки для файлових баз даних/реєстрів локалі. Вони не є папками контенту.**

Фізичні контентні файли mavik.name — MP3, EPUB, обкладинки, зображення, завантаження та інші binaries — лежать у спільному файловому сховищі сайту. Вони не дублюються по `uk`, `en`, `es`, `fr`, `de` лише через локаль.

Окремими для кожної локалі є тільки:
- файлові бази/реєстри;
- bindings на спільні фізичні файли;
- locale-specific metadata;
- publication state;
- порядок/видимість;
- індекси та службовий locale-state.

Приклад:
- один MP3 фізично лежить один раз у загальному сховищі;
- `uk`-база містить binding на цей MP3 і показує його в українській музиці;
- `en`-база може не містити binding і не показувати його;
- інший MP3 може бути прив'язаний тільки до `en`;
- один і той самий фізичний файл може бути прив'язаний до кількох локалей із різними назвами, описами, порядком, статусом та metadata.

## Канонічна модель R216

Фізичне файлове сховище контенту залишається загальним у штатній структурі сайту. Окрема locale-структура стосується **лише баз даних**:

```text
/_site-state/locales/
  uk/
    books.json
    blog.json
    music.json
    pages.json
    announcements.json
    bindings.json
    indexes/
  en/
    books.json
    blog.json
    music.json
    pages.json
    announcements.json
    bindings.json
    indexes/
  es/
  fr/
  de/
```

Жорсткий поділ відповідальності:
- **загальне файлове сховище сайту** = фізичні файли контенту;
- **locale folder** = тільки база даних/реєстри та bindings конкретної локалі.

Не створювати `uk/books/`, `en/music/` тощо як дубльовані сховища фізичних книжок або музики лише заради локалізації.

## Безпека локалей

1. Кожна локаль має власну незалежну writable файлову базу.
2. Операція запису/видалення/unpublish для `en` працює тільки з `/_site-state/locales/en/...` і не має права змінювати `uk`.
3. Boss не передає довільні filesystem paths. CORE будує шлях до locale-бази з валідованого locale id і content type.
4. Видалення запису з locale-бази не означає фізичного видалення контентного файла зі спільного сховища.
5. Фізичне видалення shared file дозволяється лише окремою cleanup-операцією після перевірки, що файл більше не має bindings у ЖОДНІЙ локалі.
6. Якщо файл має хоча б один binding у будь-якій локалі, cleanup не має права його видалити.
7. Для кожної локалі окремо зберігаються title, description, excerpt, alt/caption, publication state, sort/order, visibility та інша locale-specific metadata.
8. Одна локаль може мати матеріал, якого немає в іншій. Це нормальний стан, а не parity defect.
9. Hreflang створюється лише коли існує реальний еквівалентний counterpart між локалями.
10. CORE deploy не перезаписує locale databases. Content patches змінюють лише заявлені locale databases/bindings і, за потреби, додають фізичні файли в загальне файлове сховище.
11. Backup/rollback locale-бази повинен підтримувати локальний scope: EN database rollback не повинен вимагати rollback UK database.
12. Self-test повинен перевіряти cross-locale isolation, broken bindings та orphan shared files.

## Контентні типи

Та сама модель обов'язкова щонайменше для:
- книг/EPUB;
- блогу;
- музики;
- анонсів;
- інформаційних/редакційних сторінок;
- обкладинок та інших media bindings;
- майбутніх locale-aware content types.

## Boss

Boss працює з активною локаллю або явним набором локалей.

Для матеріалу повинно бути можливо:
- додати binding у одну чи кілька locale-баз;
- прибрати binding лише з конкретної локалі;
- змінити locale-specific title/description/metadata;
- бачити, в яких локалях є binding;
- не зачіпати bindings інших локалей.

Для блогу — явний checkbox/multi-select активних локалей публікації. Дефолт може бути `UA+EN`, але остаточний scope задає автор.

## Приклад музики

Допустимий стан:
- UK database: Track A, Track B, Track C;
- EN database: Track B, Track D, Track E.

Track B використовує той самий фізичний MP3 у загальному сховищі, але має незалежні UK/EN metadata та publication settings.

## Пріоритет

Цей документ має пріоритет над будь-яким попереднім формулюванням, яке можна було зрозуміти так, ніби самі контентні файли потрібно розкладати по окремих locale-папках.

Правильний канон: **спільні фізичні файли + окремі папки тільки для locale-баз даних/реєстрів/bindings**.
