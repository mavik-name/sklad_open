# MAVIK.NAME — LOCALIZATION ARCHITECTURE CANON

Дата: 2026-08-19
Статус: **HARD ARCHITECTURE CANON**

## Базовий принцип

Англійська версія mavik.name є **функціональним дзеркалом української версії** на тому самому CORE. Вона не є окремим сайтом, окремою оболонкою або набором вручну скопійованих сторінок.

Єдине функціональне CORE/ядро обслуговує UA, EN та майбутні ES/FR/DE. Різниця між локалями складається з:
1. системних/інтерфейсних перекладів із locale/lang files;
2. окремо перекладеного або окремо створеного користувацького контенту, який встановлюється content patches/overlays.

**Функціональна дзеркальність не означає обов'язкову контентну ідентичність 1:1.** Українська й англійська локалі можуть мати різний набір матеріалів, якщо це виправдано аудиторією, контекстом або редакційним рішенням автора.

## Жорсткий поділ CORE і CONTENT

### CORE / ядро

CORE відповідає за:
- маршрути та route capabilities;
- layout/shell;
- меню, footer, reader controls, кнопки, accessibility;
- desktop/mobile responsive behavior;
- генератори головної, каталогів, блогу та інших projections;
- locale routing і language switcher;
- canonical/hreflang/sitemap/JSON-LD/OG/Twitter механіку;
- Boss/self-tests;
- media pipeline;
- кешування, deploy/rollback, security та crawler accessibility.

CORE **не повинен містити перекладений літературний або редакційний контент як частину логіки ядра**.

### LANG / locale files

Через `lang`/locale files перекладаються лише системні та інтерфейсні тексти, зокрема:
- назви пунктів меню;
- кнопки;
- системні підписи;
- aria-labels;
- стандартні повідомлення;
- стандартні назви блоків;
- інші тексти оболонки, що не є авторським контентом.

Lang files не є сховищем книжок, блогових статей, сторінок автора, анонсів або інших великих контентних матеріалів.

### CONTENT / контент

Користувацький контент перекладається або створюється **окремо від CORE** і завантажується через PATCH/OVERLAY без втручання в ядро.

До content patches належать, зокрема:
- переклади книг і EPUB;
- тексти блогу;
- сторінки «Автор», «Контакти», «Захист/Безпека», «Анонс» та інші редакційні/інформаційні тексти;
- locale-specific metadata/excerpt/alt/caption;
- матеріали, що існують лише в одній локалі за прямим редакційним рішенням;
- інші авторські або редакційні матеріали.

Content patch не повинен модифікувати CORE PHP/JS/CSS/templates або дублювати shell/layout/reader controls. Якщо для встановлення перекладу потрібно змінити ядро, це означає дефект CORE і він виправляється окремим CORE-релізом.

## Функціональна дзеркальність локалей

1. Якщо CORE підтримує певний тип публічної сторінки або функціональний блок у UA, та сама функціональна можливість має бути доступна активній локалі через спільне CORE.
2. Структура shell, функціональність, adaptive behavior і controls між UA та EN мають бути однаковими.
3. Локаль може відрізнятися не лише мовою UI, а й фактичним набором встановленого locale-content payload.
4. Не вимагати штучного 1:1 дублювання контенту. Матеріал може бути потрібен лише українській аудиторії або лише англомовній аудиторії.
5. Hreflang створювати лише для реальної пари еквівалентних матеріалів. Якщо counterpart відсутній свідомо, не генерувати фальшиву пару.
6. Якщо EN-контент для конкретного UA-матеріалу ще не встановлений або взагалі не передбачений, CORE не повинен створювати фальшиву індексовану EN-заглушку.
7. Після встановлення locale content patch усі штатні projections — головна, каталог, блог, sitemap, metadata, internal links і hreflang там, де є counterpart — повинні оновлюватися механізмом CORE автоматично.
8. Майбутні ES/FR/DE підключаються тим самим механізмом через locale registry/lang files/content patches, без копіювання EN-специфічного коду.

## Блог

За замовчуванням кожен новий UA-пост отримує повну EN-версію одночасно. Водночас контентні набори локалей не зобов'язані бути 1:1: автор може свідомо позначити окремий запис як `UA-only` або `EN-only`, якщо матеріал не потрібен іншій аудиторії.

Архітектурно це реалізується так:
- стандартний Boss/публікаційний workflow готує UA + EN;
- для свідомих винятків передбачити explicit locale scope (`UA-only`, `EN-only`, надалі інші локалі);
- сам переклад зберігається/доставляється як content state/patch, а не вбудовується в CORE;
- CORE лише забезпечує route capability, shell, publication projection, sitemap/hreflang та self-test;
- зміна UA-поста повинна позначати EN payload як такий, що потребує синхронізації, якщо між ними існує locale pair.

## Книги

Book patch постачає лише locale-content edition: переклад книги, metadata, EPUB та потрібні content assets/state. Reader shell, меню, «Back to top», адаптивність, SEO-механіка та інші стандартні функції забезпечує CORE.

Книга може існувати лише в одній локалі, якщо так вирішено редакційно. Hreflang створюється лише коли існує реальний counterpart.

## R216

R216 має реалізувати саме цей поділ:
- виправити CORE так, щоб EN була функціональним дзеркалом UA;
- винести системні переклади в locale/lang layer;
- не вбудовувати переклади книг/блогу/редакційних сторінок у логіку CORE;
- гарантувати, що окремі locale content patches встановлюються без модифікації ядра і автоматично підхоплюються всіма projections;
- підтримати locale-specific content scope без примусового 1:1 дублювання матеріалів.

## Заборона регресії

Надалі заборонено:
- створювати окремий EN shell, який розходиться з UA;
- виправляти відсутній стандартний UI через кожен book/content patch;
- дублювати CORE-функції у locale patches;
- вбудовувати авторський перекладений контент у PHP/JS/CSS ядра;
- примусово створювати counterpart, якщо матеріал свідомо locale-specific;
- створювати локалізаційний механізм, специфічний лише для EN, якщо він може бути locale-neutral.

Останнє пряме рішення автора щодо архітектури локалізації має найвищий пріоритет над попередніми робочими трактуваннями.
